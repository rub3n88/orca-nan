# Informe vigía — 2026-09-13

**NaN ha publicado un CLI oficial que se llama `nan`.** Es una colisión de nombre con nuestro
script y, de paso, cambia el terreno para el resto del proyecto. No he tocado código: la decisión
(renombrar, convivir o detectar) es de producto y la tiene que tomar Rubén. Esto es el análisis.

## Qué cambió fuera

### 1. CLI oficial `nan` (lo gordo)

[`helmcode/nan-cli`](https://github.com/helmcode/nan-cli) — Go, `v0.1.1`, repo creado el
2026-05-21 y con push el 2026-09-12. Documentado en la página nueva
[`/docs/nan-cli`](https://nan.builders/docs/nan-cli) (`src/content/docs/nan-cli.mdx`).

- **Se instala como `nan`**: `curl -fsSL https://nan.builders/install | bash` →
  `INSTALL_DIR="${INSTALL_DIR:-/usr/local/bin}"`, binario `nan`. La propia doc ofrece como
  alternativa `INSTALL_DIR="$HOME/.local/bin"`, que es **exactamente** la ruta que nuestro README
  recomienda para el symlink: ahí no habría colisión de PATH, habría **sobrescritura** silenciosa.
- **Qué hace**: `nan` a secas abre una TUI (pestañas Profile · Usage · Models · Costs · Setup ·
  About). Subcomandos reales (cobra): `nan me`, `nan metrics usage`, `nan auth login|logout`,
  `nan --version`. Su valor real hoy es la pestaña **Setup**, que escribe la config de OpenCode,
  Codex, Pi y Factory AI (`droid`) por ti.
- **No tiene** `quota`, `usage`, `models`, `billing`, `ping`, `status` ni `config`. Si su binario
  gana en el PATH, los 11 botones del panel y todo el README producen errores de cobra
  («unknown command»), no resultados.
- **Su parte de uso está rota**: autentica con la cookie de sesión de Discord
  (`nan_session`, `internal/session/session.go`), no con la API key, y la propia doc avisa de que
  `nan auth login` apunta a un endpoint de Discord retirado que devuelve 404. Es decir: Profile,
  Usage y Costs no funcionan hoy. Lo nuestro (Bearer con la API key) sí.
- **Ficheros**: guarda `~/.config/nan/session.json` (0600), el mismo directorio que nuestro
  `~/.config/nan/api-key`. No se pisan, pero conviven. Cuando metes la key en la pestaña Setup, la
  guarda como `apiKey` dentro de ese `session.json`.

En esta máquina, ahora mismo, no está instalado (`/usr/local/bin/nan` no existe; `nan` resuelve a
`~/.local/bin/nan → dev/dinacode/orca-nan/bin/nan`) y en el PATH de Rubén `~/.local/bin` va antes
que `/usr/local/bin`. O sea: no hay incendio hoy, pero cualquier usuario de NaN que siga la doc
oficial se lleva el conflicto puesto.

### 2. `cloud-api` sube de categoría: de ingeniería inversa a semioficial

`internal/api/client.go` del CLI oficial:

```go
const BaseURL = "https://cloud-api.nan.builders/api"
// GetMe() -> /auth/me · GetMetricsUsage() -> /metrics/usage · GetAgentsModels() -> /agents/models
```

Es la misma base y dos de las rutas que sacamos del bundle del SPA. Ya no es solo el panel web:
NaN mantiene código propio contra ellas. Esto toca directamente la condición (a) del plan upstream
de `NOTAS.md` («tiene sentido si NaN documenta o estabiliza cloud-api»). Matices: sigue **sin**
aparecer nada de uso/cuota en `openapi.json` (sin cambios hoy), `/api/usage/quota` —la que de
verdad usamos— no la toca el CLI oficial, y ellos entran con cookie, no con la key.

### 5. Punto ciego del propio vigía (encontrado por el camino)

`scripts/vigia.sh` baja los ficheros con `curl -sfL … || true`: si un fichero **se renombra**, el
`curl` falla, el bucle de comparación lo salta (`[ -s "$f" ] || continue`) y el snapshot viejo se
queda tal cual **sin avisar**. Es lo que ha pasado con `getting-started.md` (404 desde la reorg):
teníamos guardadas 39 líneas de una página que hoy tiene 167 y empieza distinto. Lo mismo pasará
con cualquier otra doc que renombren.

| Pieza | Afectada |

| `bin/nan` | Sí — el nombre del comando. El código funciona: `nan quota`, `nan models` y `nan ping` probados hoy contra la API real, correctos |
| `panel.html` | Sí — 11 botones escriben `nan …` en la terminal del usuario |

## Opciones

**A. Renombrar nuestro comando** (p. ej. `nanq`, `nanu`, `orca-nan`) y dejar `nan` para el oficial.
- A favor: cero ambigüedad, para siempre; NaN tiene el nombre y la marca, la pelea está perdida.
- En contra: rompe a los usuarios instalados (symlink, PATH, muscle memory), hay que tocar README,
  los 11 botones del panel, los textos del panel y del script, y subir versión menor del plugin.
  Además el plugin dejaría de leerse como «usa el `nan` de NaN».

**B. Convivir con detección.** Mantener `nan` y que el script detecte al oficial:
si `command -v nan` resuelve a otro binario, avisar y ofrecer el alias. Publicar en el README la
instalación como `nan` **o** como nombre alternativo, a elección.
- A favor: no rompe nada hoy; el conflicto solo aparece si el usuario instala el oficial.
- En contra: el aviso llega tarde (cuando ya te han sobrescrito el symlink no hay script que avise),
  y el panel seguiría escribiendo `nan …` a ciegas.

**C. Renombrar y dejar un `nan` que reenvía.** Comando real `nanq`; si `nan` no existe en el PATH,
el README propone el symlink de compatibilidad.
- A favor: transición suave.
- En contra: dos nombres que mantener y explicar.

**D. Rendirse al oficial y reenfocar.** Si NaN arregla su login y sus pestañas Usage/Costs, nuestro
script pierde parte de su razón de ser y lo que queda valioso es lo que ellos no hacen: `quota` por
modelo con reset y ventana 4h, `ping` (latencia real y modelo que responde de verdad), `status` de
una línea y la integración con Orca (aviso al 80 %, panel).
- A favor: menos código que mantener.
- En contra: su uso lleva meses roto y va por cookie de Discord; apostar a que lo arreglen es
  apostar a ciegas. `/api/usage/quota` ni la tocan.

**Recomendación (a decidir por Rubén): B ahora, A si el CLI oficial coge tracción.** Hoy el oficial
tiene 0 estrellas, una release y la mitad rota; renombrar ya sería romper a los usuarios por un
conflicto que casi nadie tiene. Pero conviene dejarlo escrito en el README **ya** (una nota de dos
líneas: «si usas el CLI oficial de NaN, instala este como `nanq`») para que nadie se sorprenda, y
que el panel use el nombre que el usuario haya elegido. Añadir además un `nan config` que sepa leer
la key de `~/.config/nan/session.json` sería interop barato con el oficial.
